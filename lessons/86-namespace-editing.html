STEP 70 · NAMESPACE EDITING

Namespace編集とSdf

改名・移動と、大量編集の速さ

今日これだけ

UsdNamespaceEditorは改名・移動に合わせて参照側のPathも直し ChangeBlockは大量編集の通知をまとめる

公式情報に基づく説明

Primの名前を変えると、指していた側が壊れる

STEP 112で、存在しないPathを指すRelationshipが壊れた状態になることを見ました。Primの改名や移動は、まさにこれを引き起こします。/World/Oldを/World/Newにすれば、/World/Old/Ballを指していたRelationshipは宙に浮きます。

これを自分で直すのは大変です。Stage中のRelationshipとComposition Arcを全部走査し、該当するPathを書き換える必要があります。UsdNamespaceEditorは、この一連をまとめて行うAPIです。改名や移動を宣言しておき、ApplyEdits()で一度に適用します。指していた側のPathも自動で追従します。

もう一つ、合成前のLayerを直接扱うAPIがあります。STEP 12で見たSdfモジュールです。Sdf.CreatePrimInLayerで途中のPrimごとSpecを作り、Sdf.ChangeBlockで大量の編集をまとめます。

OpenUSD Academy Note

使い分けは単純です。合成後のStageを相手にするならUsd、あるLayerの記述そのものを相手にするならSdfです。UsdNamespaceEditorは前者、Sdf.CreatePrimInLayerは後者にあたります。

Python

改名すると、指していた側も直る

namespace_edit.pyPython
from pxr import Usd, UsdGeom

stage = Usd.Stage.CreateNew("t.usda")
UsdGeom.Xform.Define(stage, "/World")
UsdGeom.Xform.Define(stage, "/World/Old")
UsdGeom.Sphere.Define(stage, "/World/Old/Ball")
UsdGeom.Scope.Define(stage, "/World/Target")

editor = Usd.NamespaceEditor(stage)
print("前 :", [str(p.GetPath()) for p in stage.Traverse()])

editor.RenamePrim(stage.GetPrimAtPath("/World/Old"), "New")
print("改名:", editor.ApplyEdits())
print("後 :", [str(p.GetPath()) for p in stage.Traverse()])

editor.MovePrimAtPath("/World/New", "/World/Target/New")
print("移動:", editor.ApplyEdits())
print("後 :", [str(p.GetPath()) for p in stage.Traverse()])
実行結果Output
前 : ['/World', '/World/Old', '/World/Old/Ball', '/World/Target']
改名: True
後 : ['/World', '/World/New', '/World/New/Ball', '/World/Target']
移動: True
後 : ['/World', '/World/Target', '/World/Target/New', '/World/Target/New/Ball']

子のBallも一緒に付いてきています。ここまでは手作業でもできますが、次が本題です。

namespace_edit.py（続き）Python
# この Prim を指している Relationship を用意しておく
selection = stage.DefinePrim("/World/Sel")
rel = selection.CreateRelationship("members")
rel.SetTargets(["/World/Target/New/Ball"])

editor.RenamePrim(stage.GetPrimAtPath("/World/Target/New"), "Renamed")
editor.ApplyEdits()

print("改名後のtargets:",
      [str(t) for t in selection.GetRelationship("members").GetTargets()])
実行結果Output
改名後のtargets: ['/World/Target/Renamed/Ball']

membersは/World/Target/New/Ballを指していましたが、改名に合わせて/World/Target/Renamed/Ballへ自動で書き換わりました。自分でPathを直す処理を書く必要はありません。

USDA

改名すると、何が書き換わるのか

before.usdaUSDA
def Xform "World"
{
    def Xform "Old"
    {
        def Sphere "Ball"
        {
            double radius = 0.5
        }
    }

    def "Sel"
    {
        rel members = </World/Old/Ball>
    }
}
after.usda（Old → New に改名した後）USDA
def Xform "World"
{
    def Xform "New"
    {
        def Sphere "Ball"
        {
            double radius = 0.5
        }
    }

    def "Sel"
    {
        rel members = </World/New/Ball>
    }
}

変わったのは2か所です。Prim名の"Old"が"New"になり、それを指していたrel membersの< >の中も追従しています。波括弧の中の階層はそのまま、丸括弧のMetadataも変わりません。手作業だと2か所目を忘れます。

Sdf.ChangeBlock

大量の編集は、通知をまとめる

USDは、値が変わるたびに「変わった」という通知を出します。1つずつなら軽い処理ですが、数千回続けると通知そのものが重くなります。Sdf.ChangeBlockは、その間の通知を1つにまとめるための仕組みです。

change_block.pyPython
import time
from pxr import Sdf, Usd


def build(use_block, n=3000):
    stage = Usd.Stage.CreateInMemory()
    layer = stage.GetRootLayer()
    start = time.time()
    if use_block:
        with Sdf.ChangeBlock():
            for i in range(n):
                Sdf.CreatePrimInLayer(layer, "/P%d" % i).specifier = Sdf.SpecifierDef
    else:
        for i in range(n):
            Sdf.CreatePrimInLayer(layer, "/P%d" % i).specifier = Sdf.SpecifierDef
    return time.time() - start


print("ChangeBlock なし: %.3f 秒" % build(False))
print("ChangeBlock あり: %.3f 秒" % build(True))
実行結果Output
ChangeBlock なし: 0.604 秒
ChangeBlock あり: 0.029 秒

3000個のPrimを作るだけで、20倍以上の差が出ました。変換ツールのように大量のPrimやAttributeを一度に書く処理では必ず使います。

OpenUSD Academy Note

ChangeBlockの中では、Stage側からの読み取りをしてはいけません。通知が止まっているためStageの状態が更新されておらず、古い値が返ることがあります。「Sdfで書くだけ」に徹して、読むのはブロックを抜けてからにします。

Sdf.CreatePrimInLayer

途中のPrimは over で作られる

create_prim_in_layer.pyPython
from pxr import Sdf, Usd

stage = Usd.Stage.CreateInMemory()
layer = stage.GetRootLayer()

spec = Sdf.CreatePrimInLayer(layer, "/A/B/C")
spec.specifier = Sdf.SpecifierDef

print("中間のSpecifier:", [(str(p.path), str(p.specifier)) for p in layer.rootPrims])
print("Traverse    :", [str(p.GetPath()) for p in stage.Traverse()])
print("TraverseAll :", [str(p.GetPath()) for p in stage.TraverseAll()])

for path in ("/A", "/A/B"):
    layer.GetPrimAtPath(path).specifier = Sdf.SpecifierDef
print("中間もdefにすると Traverse:", [str(p.GetPath()) for p in stage.Traverse()])
実行結果Output
中間のSpecifier: [('/A', 'Sdf.SpecifierOver')]
Traverse    : []
TraverseAll : ['/A', '/A/B', '/A/B/C']
中間もdefにすると Traverse: ['/A', '/A/B', '/A/B/C']

ここは間違えやすい挙動です。Sdf.CreatePrimInLayerは途中の/Aと/A/Bも作りますが、Specifierはoverのままです。STEP 85で見たDefault PredicateはPrimIsDefinedを含むので、overの枝ごと走査から外れます。だからTraverse()が空になりました。

TraverseAll()には出てくるので、「作ったはずなのにTraverse()に出ない」ときは、この中間のSpecifierを疑います。UsdGeom.Xform.Define()のようなDefine系のAPIは、途中のPrimもdefで作るのでこの問題は起きません。

Beginner notes

Relocatesとの違い

OpenUSD Academy Note

STEP 53のRelocatesも「Pathを移す」仕組みでした。違いはどこを変えるかです。

Relocatesは合成のときに移す指示で、参照先のファイルは変わりません。他人のAssetの中の名前を、自分のシーンでだけ読み替えたいときに使います。UsdNamespaceEditorは記述そのものを書き換えます。自分が管理しているファイルの構造を整理するときに使います。

「相手のファイルを触れないならRelocates、自分のファイルなら NamespaceEditor」と覚えると選びやすくなります。

よくある間違い

編集したのに反映されない・壊れる

ApplyEditsを呼び忘れる

RenamePrim()は編集を積むだけです。ApplyEdits()で初めて適用されます。

自分でPathを書き換えてRelationshipを直し忘れる

Sdf.CopySpecと削除で移動すると、指していた側は自分で直す必要があります。UsdNamespaceEditorなら追従します。

ChangeBlockの中でStageを読む

通知が止まっているので、古い値が返ることがあります。書くことに徹し、読むのは抜けてからにします。

Sdf.CreatePrimInLayerで作ったのにTraverseに出ない

途中のPrimがoverのままです。Traverse()はoverの枝を通りません。中間もdefにするか、Define()系のAPIを使います。

他人のAssetをNamespaceEditorで整理する

相手のファイルを書き換えることになります。自分のシーンでだけ読み替えたいならRelocatesです。

Glossary

このレッスンの用語

UsdNamespaceEditor
Primの改名や移動を行い、指していたRelationshipのPathも追従させるPython API。
ApplyEdits
積んだ編集をまとめて適用するメソッド。呼ぶまで反映されない。
Sdf.ChangeBlock
その間の変更通知を1つにまとめる仕組み。大量編集で大きく速くなる。中でStageを読んではいけない。
Sdf.CreatePrimInLayer
Layerに直接PrimSpecを作るPython API。途中のPrimはoverで作られる。
PrimSpec
あるLayerに書かれた、合成前のPrimの記述。Specifierや型名を持つ。
