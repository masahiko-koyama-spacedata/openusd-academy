要点1

「1つのPrim＝1か所」ではない

この教材を通していちばん大事な考え方です。画面に見える1つのPrimは、複数のファイルに書かれた記述が重なった結果です。だから次のことが言えます。

要点2

「見えない」には理由が5つある

教材の中で何度も出てきた切り分けです。どれも別の仕組みなので、一つずつ確かめます。

  1. そのPathにPrimが無い — 綴りの誤り
  2. STEP 49 overだけで定義されていない — IsDefined()がFalse
  3. STEP 50 classでabstract — IsAbstract()がTrue
  4. STEP 87 active = falseで構成から外れている
  5. STEP 88 Payloadが未Load — 中身がまだ来ていない

これにvisibility = invisibleを加えた判定を、STEP 92 Hydraのwhy_not_drawnとして関数にしました。どれにも当てはまらなければ、原因はSTEP 119 参照の解決失敗か、カメラか、Renderer側です。

要点3

数えるものが決まれば、書く量が決まる

STEP 33 Primvarの章で扱った、値の個数の対応です。実務で最も頻繁に確認することになります。

Face 2枚・Point 6個・Face Vertex 8個 の板の場合まとめ
constant     → 1 個   （Prim全体）
uniform      → 2 個   （len(faceVertexCounts)）
vertex       → 6 個   （len(points)）
varying      → 6 個   （len(points)）
faceVarying  → 8 個   （sum(faceVertexCounts)）

indices を付けた場合は、個数を満たすのは indices のほう

要点4

境界を決めると、壊れなくなる

設計の章はすべて、この一点に集約されます。

Python

読み方をひとつの関数にまとめる

最後に、ここまでの道具をまとめて「なぜこの値になったのか」を出す関数を置きます。値が思ったとおりでないとき、この順に見れば原因にたどり着けます。

why.pyPython
from pxr import Sdf, Usd, UsdGeom


def why(stage, path, prop_name):
    """あるPropertyの値が、どこから来たのかを順に出す。"""
    prim = stage.GetPrimAtPath(path)
    if not prim:
        print("Primが無い:", path, "… active / load / Pathの綴りを見る")
        return

    print("Specifier      :", prim.GetSpecifier())
    print("型             :", prim.GetTypeName() or "(型なし)")
    print("Instance Proxy?:", prim.IsInstanceProxy())

    # 1. どのLayerがこのPrimに寄与しているか
    print("-- Prim Stack --")
    for spec in prim.GetPrimStack():
        print("  ", spec.layer.GetDisplayName(), spec.path)

    # 2. そのPropertyはどこに書かれたか
    attr = prim.GetAttribute(prop_name)
    if not attr:
        print("そのPropertyは無い:", prop_name)
        return
    print("-- Property Stack --")
    for spec in attr.GetPropertyStack(Usd.TimeCode.Default()):
        print("  ", spec.layer.GetDisplayName(), "=", spec.default)

    # 3. 最終的な値
    print("解決された値 :", attr.Get())
    print("書かれている? :", attr.HasAuthoredValue(), "（Falseなら Schema の既定値）")


stage = Usd.Stage.Open("park.usda")
why(stage, "/Park/Bench", "primvars:displayColor")

Prim Stackで「どのLayerがこのPrimに寄与したか」、Property Stackで「その値をどのLayerが書いたか」、最後に解決された値を見ます。HasAuthoredValue()がFalseなら、誰も書いておらずSchemaの既定値が使われた、と分かります。Usd.Stage.Open()の結果を必ず変数へ入れている点にも注意してください。

よくある間違い

最後にもう一度、つまずきやすい所を並べる

Propertyを含むPrim bodyを一行で書く

def Cube "A" { double size = 1 }は構文エラーです。中身が空の{ }だけは一行で書けます。この教材でも実際に3か所やってしまい、usdcatで見つけました。

Stageを変数に入れずに使う

for p in Usd.Stage.Open("a.usda").Traverse():と書くと、Stageがすぐ破棄されてInvalid range starting with expired primになります。必ず変数へ入れて保持します。

合成後の値と、あるLayerに書いた値を混同する

prim.GetSpecifier()が返すのは合成後のSpecifierです。overで書いたつもりでもdefが返ることがあります。書いた側を見たいならlayer.GetPrimAtPath(path).specifierです。

Prototypeの番号で同一性を判断する

/__Prototype_1のような名前は安定しません。同じファイルを開き直すだけで変わります。比べるならGetPrototype()が返すオブジェクトそのものです。

既定値を「値が無い」と読む

Schemaの既定値は「その値である」です。subdivisionSchemeを書かなければcatmullClarkとして扱われ、書いたはずの角が丸くなります。

誤検知する検査を書く

Instanceの子をGetChildren()で数えると0になり、正しいAssetを壊れていると報告します。誤検知する検査は、無いより悪いことがあります。

エラーにならずに間違う場所

教材を作る過程で実際に踏み、本文に書き残したものです。どれも例外が出ないため、知らないと気付けません。

Prototypeの番号を当てにする

同じファイルを2回開いたら割り当てが変わりました。GetPrototype()どうしを比べます。（STEP 110）

未Loadの状態でArcの種類を調べる

階層を移してRelationshipを直し忘れる

存在しないPathを指したBindingが静かに残りました。（STEP 105）

同じ名前のCameraを複数置く

usdrecord --cameraがどれを使うか決まらず、真っ白になりました。（STEP 122）

Instanceの子を GetChildren() で数える

正しいシーンで誤検知しました。中身はPrototype側にあります。（STEP 120）

Stageを変数に持たずに走査する

途中で片付けられて例外になります。（STEP 120）

1行にPropertyを書いたPrimを書く

def Cube "A" { double size = 1 }は構文エラーです。1行で書けるのは空のボディだけです。

Glossary

Composition

Layer / Prim / Property

Asset / Scene
再利用される単位と、それを配置した結果。触る場所が分かれている。
Stack
