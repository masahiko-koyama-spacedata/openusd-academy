STEP 99 · BROADCASTED REFINEMENT

Broadcasted Refinement

下流の1か所を書き換えて、対象の全部へ一度に届かせます

今日これだけ

Inheritsの受け口に下流からOpinionを足せば Assetを書き換えずに対象の全Instanceへ一度に届く

公式情報に基づく説明

Assetを書き換えずに、共有先を一括で変える

ここまでは「1体ずつ差を付ける」話でした。Broadcasted Refinementは逆で、共有している一群へ同じ変更を一度に配るやり方です。broadcastは放送という意味で、1か所へ書いた内容が対象全体へ届くことを指しています。

素直に考えると、共有元のAssetファイルを直せば全部変わります。しかしそれはやってはいけない直し方です。そのAssetは他のシーンからも参照されているので、無関係な場所まで巻き込みます。Assetは上流の資産で、下流のシーンから書き換えるものではありません。

正しいやり方は、STEP 46のInheritsを受け口として使うことです。Asset側にはあらかじめ空のclassを置き、そこからInheritsしておきます。下流のシーンは、Assetファイルには一切触れず、自分のLayerでそのclassへOpinionを書きます。Inheritsを経由して、参照している全Instanceへ届きます。

OpenUSD Academy Note

受け口にはInheritsとSpecializesのどちらも使えます。違いはSTEP 52のLIVERPSでの強さです。InheritsはReferenceより強く、SpecializesはReferenceより弱い位置にいます。この差が効くのは同じPropertyに競合するOpinionがあるときだけです。

USDA

Asset側は受け口を置いておくだけ

chair.usda — 上流のAssetUSDA
class Xform "_Style"
{
}

class Xform "_Worn"
{
}

def Xform "Chair" (
    inherits = </_Style>
)
{
    def Sphere "Seat"
    {
        double radius = 0.5
    }
}

classはSTEP 42で見たとおり、それ自体は描画されない、上書き用の型です。中身は空で構いません。ここで大事なのは受け口を最初から用意しておくことで、これはAssetを設計する時点での判断になります。用意していないAssetに後から差し込むことはできません。

このUSDAファイルを開く

Python

下流のLayerからclassへ1か所書く

broadcast.pyPython
from pxr import Gf, Sdf, Usd, UsdGeom

stage = Usd.Stage.Open("scene.usda")   # 下流のシーン
print("初期:", [str(p.GetPath()) for p in stage.GetPrototypes()])

# chair.usda には触らない。下流のLayerで class へ Opinion を足す
over = stage.OverridePrim("/_Style/Seat")
UsdGeom.PrimvarsAPI(over).CreatePrimvar(
    "displayColor", Sdf.ValueTypeNames.Color3fArray,
    UsdGeom.Tokens.constant).Set([Gf.Vec3f(0.9, 0.4, 0.1)])

print("全体へ1か所:", [str(p.GetPath()) for p in stage.GetPrototypes()])
for name in "ABC":
    print("   /World/%s/Seat -> %s" % (name,
        stage.GetPrimAtPath("/World/%s/Seat" % name)
             .GetAttribute("primvars:displayColor").Get()))
実行結果Output
初期: ['/__Prototype_1']
全体へ1か所: ['/__Prototype_2']
   /World/A/Seat -> [(0.9, 0.4, 0.1)]
   /World/B/Seat -> [(0.9, 0.4, 0.1)]
   /World/C/Seat -> [(0.9, 0.4, 0.1)]

1か所書いただけで3体すべてに届きました。そしてchair.usdaは変更していません。

Prototypeの数が1つのままである点も確認してください。共有は壊れていません。ただし名前が/__Prototype_1から/__Prototype_2へ変わっています。中身が変わったので、Prototypeが作り直されたためです。数は変わらないが、同じPrototypeではないという点に注意します。

グループを分ける

受け口を分ければ、その群だけのPrototypeができる

Broadcastは「全部」だけではありません。受け口のclassを分け、対象のInstanceだけにInheritsを足せば、その群だけに届きます。

broadcast.py（続き）Python
# B と C にだけ、もう一つの class を Inherits させる
for name in "BC":
    stage.GetPrimAtPath("/World/" + name).GetInherits().AddInherit("/_Worn")

worn = stage.OverridePrim("/_Worn/Seat")
UsdGeom.PrimvarsAPI(worn).CreatePrimvar(
    "displayColor", Sdf.ValueTypeNames.Color3fArray,
    UsdGeom.Tokens.constant).Set([Gf.Vec3f(0.35, 0.25, 0.2)])

print("一部グループへ:", [str(p.GetPath()) for p in stage.GetPrototypes()])
for name in "ABC":
    prim = stage.GetPrimAtPath("/World/" + name)
    print("   /World/%s -> Prototype %s / 色 %s" % (name,
        prim.GetPrototype().GetPath(),
        stage.GetPrimAtPath("/World/%s/Seat" % name)
             .GetAttribute("primvars:displayColor").Get()))
実行結果Output
一部グループへ: ['/__Prototype_2', '/__Prototype_3']
   /World/A -> Prototype /__Prototype_2 / 色 [(0.9, 0.4, 0.1)]
   /World/B -> Prototype /__Prototype_3 / 色 [(0.35, 0.25, 0.2)]
   /World/C -> Prototype /__Prototype_3 / 色 [(0.35, 0.25, 0.2)]

Prototypeが2つになり、BとCが同じ/__Prototype_3を共有しています。これが「対象グループ用の新しいPrototypeを作る」ということです。100体のうち30体を汚した見た目にしたいなら、その30体に/_WornをInheritsさせるだけで、Prototypeは2つで済みます。

Specializes

Specializesでも配れる。ただし競合すると負ける

「SpecializesはReferenceより弱い」と聞くと、broadcastに使えないように思えます。しかしそれは正確ではありません。弱いのは競合したときだけで、競合しない内容はきちんと届きます。実際に3つの場合を確かめました。Asset側のSeatがdisplayColorを持っている状態で、Specializes経由のclassへ書き込んでいます。

書いたものAsset側に同じものがあるか結果
primvars:displayColorある届かない。Reference側の値が勝つ
primvars:myTag（新しいProperty）ない届く
Badge（新しい子Prim）ない届く
実行結果Output
(1) 競合あり displayColor : [(0.15, 0.35, 0.85)] ← Reference側が勝つ
(2) 競合なし primvars:myTag : [worn]           ← Specializes 経由で届く
(3) 新しい子Prim /World/A/Badge : True 半径 0.1

まとめると、Specializesは新しいOpinionやfallbackをbroadcastできますが、既にAssetが持っている値の上書きには向きません。Asset側の値を確実に上書きしたいならInheritsを選びます。逆に「Assetが指定していなければこれを使う」という下敷きを配りたいなら、Specializesのほうが意図に合います。

OpenUSD Academy Note

「Specializesは効かない」と単純化すると、公式の演習がSpecializeで変更を配っていることと食い違います。正しくは競合したときにReferenceに負けるで、それ以外は普通に届きます。強さの話は常に「同じ対象に複数のOpinionがあるとき、どれが選ばれるか」の話であって、Arc自体の有効・無効の話ではありません。

Assetファイルそのものを書き換える

結果だけ見れば同じに見えますが、そのAssetを参照している他のシーンまで変わります。Broadcasted Refinementは下流のLayerから行うのが要点で、Assetを直すのは別の作業です。

受け口のclassを用意していないAssetに使おうとする

Inheritsが無ければ届く経路がありません。後から足すにはAsset側の変更が必要になります。再利用されるAssetでは、受け口を最初から設計に入れておきます。

SpecializesとInheritsを取り違える

Assetが既に持っている値を上書きしたいのにSpecializesを使うと、Referenceのほうが強いため、そのPropertyだけ届きません。新しいPropertyや子Primは届くので、一部だけ反映されて原因が分かりにくくなります。上書きしたいならInheritsです。

Prototypeが「同じ」だと思い込む

数が1つのままでも、中身が変われば別のPrototypeとして作り直されます。番号の文字列で同一性を判断しないでください。

class名を通常のPrimと同じ場所に置く

classは描画されませんが、Stageの階層には現れます。_で始めるなど、通常のPrimと見分けられる名前にしておくと、後から読む人が迷いません。

Glossary

このレッスンの用語

Broadcasted Refinement
Inheritsなどの受け口へ下流からOpinionを足し、対象の全Instanceへ一度に変更を届ける方法。
受け口のclass
Asset側にあらかじめ置いておく空のclass。下流はここへ書き込むことで、Assetを変更せずに中身へ届かせられる。
Opinion
あるLayerに書かれた、そのPropertyやMetadataについての意見。合成の強さの順に評価される。
Inherits
classからの継承を表すComposition Arc。LIVERPSでReferenceより強いため、参照で持ち込んだ値を上書きできる。
Specializes
Inheritsと似た形だが、LIVERPSでReferenceより弱いComposition Arc。競合しない新しいOpinionや子Primはbroadcastできるが、Assetが既に持つ値の上書きには向かない。
