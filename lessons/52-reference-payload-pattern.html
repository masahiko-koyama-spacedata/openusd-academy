Reference/Payload Pattern

外からはReference、内からはPayload。この組み合わせが基本形です

今日これだけ

外→入口はReference、入口→中身はPayload

公式情報に基づく説明

2つのArcを役割で使い分ける

ここまでの章で作ってきたAssetの形を、一つのパターンとしてまとめます。使う側からAssetのSTEP 73 Entry PointへはSTEP 45 Referenceを張ります。入口から中身へはSTEP 46 Payloadを張ります。この組み合わせにより、入口の情報は必ず読めるのに中身は開くかどうかを選べるという状態が作れます。

OpenUSD Academy Note

どちらか一方では成立しません。全部Referenceにすると必ず全部読み込まれ、入口だけ読むことができません。逆に外からPayloadで張ると、そのAssetがシーンに居ることすら読み込むまで分からなくなります。2段構えであることがこのパターンの本体です。

Diagram

2段のつなぎ方

USDA

外から入口へ — Reference

scene.usda（抜粋）USDA
def "Lamp_1" (
    references = @lamp.usda@
)
{
    double3 xformOp:translate = (-1.4, -1, 0)
    uniform token[] xformOpOrder = ["xformOp:translate"]
}

Referenceなので必ず読み込まれます。だから「このシーンにランプが2台ある」という事実は、どんな読み込み設定でも分かります。

USDA

入口から中身へ — Payload

lamp.usda（抜粋）USDA
def Xform "Lamp" (
    kind = "component"
    payload = @lamp_contents.usda@</Lamp>
)
{
    custom string academy:assetName = "Lamp"
    custom string academy:version = "1.0"
    float3[] extentsHint = [(-0.5, -0.06, -0.5), (0.5, 2.05, 0.5)]
}

Payloadなので、開くかどうかを読む側が選べます。開かない場合でも、この波括弧の中に書かれた情報はすべて読めます。

結果

パターンを使わない場合と比べる

同じランプ2台のシーンを、2通りの作り方で用意して測りました。片方は中身まで1枚にまとめてReferenceだけで組んだもの、もう片方がこのパターンです。

compare_patterns.pyPython
from pxr import Usd

for label, path in (("Reference のみ  ", "flat-scene.usda"),
                    ("Reference+Payload", "scene.usda")):
    counts = []
    for mode in (Usd.Stage.LoadAll, Usd.Stage.LoadNone):
        stage = Usd.Stage.Open(path, mode)
        counts.append(len(list(stage.Traverse())))
    print("%s  LoadAll %2d prims / LoadNone %2d prims"
          % (label, counts[0], counts[1]))

# Reference のみ    LoadAll 10 prims / LoadNone 10 prims
# Reference+Payload  LoadAll 10 prims / LoadNone  2 prims

Referenceだけで組んだほうは、LoadNoneを指定しても10個すべて読み込まれます。読み込みを減らす手段が存在しないということです。パターンに従ったほうは2個まで落とせます。シーンが1000台のランプになったときに、この差がそのまま効いてきます。

Python

パターンどおりか検査する

check_pattern.pyPython
from pxr import Usd


def check_pattern(asset_path):
    """入口がPayloadで中身へつないでいるかを確かめる。"""
    stage = Usd.Stage.Open(asset_path, Usd.Stage.LoadNone)
    prim = stage.GetDefaultPrim()
    if not prim:
        return "defaultPrim がない"

    if not prim.HasAuthoredPayloads():
        return "入口から中身へのPayloadがない（中身が入口に直接書かれている可能性）"
    if not stage.FindLoadable():
        return "Load制御できる箇所がない"
    return "OK"


print(check_pattern("lamp.usda"))         # OK
print(check_pattern("flat-lamp.usda"))    # 入口から中身へのPayloadがない…

パターンに従っているかは機械で確かめられます。Usd.Stage.LoadNoneで開いているので、中身がどれだけ重くても一瞬で判定できます。アセットを受け取ったときの受け入れ検査に組み込む形が実用的です。

OpenUSD Academy Note

ここでHasAuthoredPayloads()を使っているのには理由があります。Usd.PrimCompositionQueryでArcの種類を調べる方法もありますが、LoadNoneで開いた状態では、PayloadのArcが結果に出てきません。実際に手元で確かめたところ、LoadAllでは[Pcp.ArcTypeRoot, Pcp.ArcTypePayload]が返るのに対し、LoadNoneでは[Pcp.ArcTypeRoot]だけでした。開いていないPayloadは合成されていないので、当然といえば当然です。HasAuthoredPayloads()は記述の有無を見るので、Load状態に左右されません。

Beginner notes

境界は1か所だけにする

OpenUSD Academy Note

Payloadは何段にも重ねられますが、初めのうちはAssetにつき1か所にしておくと分かりやすくなります。入口の直下に1つ、というのが基本形です。段が増えると「どこまで開いているのか」を追うのが難しくなり、FindLoadable()の結果も読みにくくなります。大きなAssetを分割したくなったら、まずSTEP 85 Asset Modularityのとおり別のAssetに切り出せないかを考えます。

よくある間違い

2つのArcを取り違える

外からPayloadで張る

そのAssetがシーンに居ることすら、読み込むまで分からなくなります。外からはReferenceです。

入口から中身へReferenceで張る

必ず読み込まれてしまい、Load制御ができません。ここはPayloadです。

中身を入口に直接書く

ファイルは1枚で済みますが、読み込みを減らす手段が無くなります。上の比較のとおりです。

入口の情報をPayloadの中に置く

開かないと読めないので、パターンの利点が消えます。名乗り・パラメータ・要約は入口側です。

未Loadの状態でArcの種類を調べて判定する

開いていないPayloadはPrimCompositionQueryの結果に現れません。記述の有無を見るHasAuthoredPayloads()を使います。
